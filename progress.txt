--------------------------------------------------------------------------------
1. EXTRACTION & UNPACKING RESILIENCE (CRITICAL FOUNDATION)
--------------------------------------------------------------------------------
1.1. Nested Archive & Recursive Inner Binary Unpacking
- WHY NEEDED: 
  Vendors distribute firmware inside `.zip` files that contain a `.bin` image. 
  When the current tool unzips the file, it leaves the `.bin` untouched inside 
  the extracted directory rather than recursively running binwalk on the inner binary,
  resulting in 0 files analyzed and a false 100/100 score.
- EXECUTION PROCESS:
  1. Modify `iot_scanner/core/extractor.py` to recursively inspect all extracted 
     files.
  2. If an extracted file is a firmware image (`.bin`, `.img`, `.trx`, `.chk`), 
     automatically invoke the extraction pipeline on that file recursively up to depth 3.
  3. Standardize the output directory tree to point to the innermost root filesystem 
     (`squashfs-root`, `romfs-root`, `rootfs`).

1.2. Decompression Plugin Suite Integration (Sasquatch, Jefferson, UBI, Cramfs)
- WHY NEEDED:
  Real-world IoT devices (TP-Link, D-Link, Netgear) use non-standard, vendor-modified 
  SquashFS compression (e.g. LZMA big-endian, customized headers) or JFFS2/UBIFS. 
  Standard Linux `unsquashfs` fails silently.
- EXECUTION PROCESS:
  1. Build a Docker container containing `sasquatch` (for modified SquashFS), 
     `jefferson` (for JFFS2), `ubi_reader` (for UBIFS), and `firmware-mod-kit`.
  2. In `extractor.py`, fall back through the decompression hierarchy:
     `binwalk` -> `sasquatch` -> `jefferson` -> `ubi_reader` -> `tar/zip/lzma`.

1.3. Extraction Health Check & Fail-Safe Scoring Guard
- WHY NEEDED:
  Currently, if extraction yields 0 files, the scanner proceeds silently and calculates 
  a 100/100 "Grade A" security score because 0 findings were found. This gives a dangerous 
  false sense of security.
- EXECUTION PROCESS:
  1. In `api.py` and `main.py`, check `files_found` after extraction.
  2. If `files_found == 0` or if no POSIX rootfs structure is found, mark scan status as 
     `INCOMPLETE / EXTRACTION_FAILED`.
  3. Set Security Score to `N/A` or `Unanalyzable` and notify the user that the binary 
     is encrypted, packed, or unsupported.

1.4. Zip-Bomb, Symlink Traversal & Malicious Archive Sandboxing
- WHY NEEDED:
  Firmware images can contain symlinks pointing to `/etc/shadow` on the host or 
  malicious relative paths (`../../`) designed to overwrite server files.
- EXECUTION PROCESS:
  1. Validate canonical extraction paths using `os.path.commonpath`.
  2. Restrict maximum extracted disk quota (e.g. 5GB max) and max file count (50,000 files).
  3. Run extraction inside unprivileged Docker/gVisor sandboxes.

2. VULNERABILITY INTELLIGENCE & SBOM COMPLIANCE
--------------------------------------------------------------------------------
2.1. Real-Time OSV & NVD 2.0 API Integration with Local SQLite Caching
- WHY NEEDED:
  The current tool relies on a static `cve_db.json` (contains only ~8 CVEs) and a free 
  CIRCL endpoint that returns 404s. Real-world firmware has hundreds of packages.
- EXECUTION PROCESS:
  1. Implement `iot_scanner/core/cve_client.py` integrating the Google OSV API 
     (`https://api.osv.dev/v1/query`) and NVD 2.0 API.
  2. Implement an offline SQLite cache (`cve_cache.db`) storing CVE metadata, CVSS v3.1 
     scores, vector strings, and publication dates.
  3. Add CISA KEV (Known Exploited Vulnerabilities) tags to highlight CVEs actively 
     weaponized in the wild.

2.2. Software Bill of Materials (SBOM) Generation (CycloneDX & SPDX)
- WHY NEEDED:
  Mandated by US Executive Order 14028 and the EU Cyber Resilience Act (CRA) for all IoT 
  device compliance audits.
- EXECUTION PROCESS:
  1. Create `iot_scanner/core/sbom_generator.py` using `cyclonedx-python-lib`.
  2. Catalog components, versions, licenses, and SHA256 package hashes.
  3. Export downloadable `cyclonedx.json` and `spdx.json` from the Web UI and CLI.

2.3. Package Manager Manifest Parsing
- WHY NEEDED:
  Regex scanning of raw binaries miss packages. OpenWrt, Debian-based IoT, and Yocto 
  leave package manifests on disk (`/usr/lib/opkg/status`, `/var/lib/dpkg/status`).
- EXECUTION PROCESS:
  1. Add parsers for OPKG (OpenWrt), DPKG (Debian/Ubuntu), and RPM manifests.
  2. Extract exact installed package versions with 100% accuracy before falling back to regex.

--------------------------------------------------------------------------------
3. BINARY ANALYSIS & STATIC DISASSEMBLY ENGINE
--------------------------------------------------------------------------------
3.1. Symbol & Call-Site Disassembly (Capstone / Radare2)
- WHY NEEDED:
  Currently, searching for `"strcpy"` greps plain ASCII strings in the first 512KB of 
  binaries, producing massive false positives even on benign static strings.
- EXECUTION PROCESS:
  1. Integrate `capstone` or `r2pipe` (Radare2) for ELF binaries.
  2. Check whether dangerous symbols (`strcpy`, `system`, `popen`) exist in the `.dynsym` / 
     import table, and check if they are called with user-controlled input buffers.

3.2. Bundled IoT Threat YARA Rules Repository
- WHY NEEDED:
  The engine logs "YARA rules directory not found" because no `.yar` files are bundled.
- EXECUTION PROCESS:
  1. Create `iot_scanner/rules/malware/` containing curated YARA rules for:
     - Mirai (and its 20+ variants: Okiru, Satori, Echobot)
     - Gafgyt / BASHLITE
     - Mozi P2P Botnet
     - Tsunami / Kaiten / Hajime
     - BrickerBot
  2. Auto-load and compile rules on server startup.

3.3. Architecture-Aware Hardening Verification (ARM, MIPS, RISC-V, x86)
- WHY NEEDED:
  IoT firmware runs predominantly on MIPS (Big/Little Endian) and ARM. Hardening checks 
  must accurately detect architecture-specific calling conventions and relocation types.
- EXECUTION PROCESS:
  1. Use `pyelftools` to inspect ELF header `e_machine` (ARM, MIPS, PPC, x86).
  2. Check for Stack Canary initialization (`__stack_chk_guard` / `__stack_chk_fail`), 
     NX (GNU_STACK segment), ASLR/PIE (`ET_DYN`), and RELRO (`DT_BIND_NOW`).

4. ARCHITECTURE, SCALABILITY & CLOUD-NATIVE BACKEND
--------------------------------------------------------------------------------
4.1. Asynchronous Distributed Task Queue (Celery + Redis)
- WHY NEEDED:
  FastAPI `BackgroundTasks` run in the same single process. Scanning a 60MB firmware 
  takes 3-5 minutes, which locks CPU threads and exhausts RAM under concurrent uploads.
- EXECUTION PROCESS:
  1. Decouple scan jobs into Celery worker tasks.
  2. Use Redis as the message broker and result backend.
  3. Add WebSocket endpoint (`/ws/scan/{scan_id}`) for real-time log streaming.

4.2. Database Upgrades & Migrations (PostgreSQL + Alembic)
- WHY NEEDED:
  SQLite suffers from write locks during concurrent scans.
- EXECUTION PROCESS:
  1. Configure SQLAlchemy async session engine supporting PostgreSQL.
  2. Setup Alembic for version-controlled database schema migrations.
  3. Store scan configurations, user identities, and scan history.

4.3. RESTful OpenAPI & Role-Based Access Control (RBAC)
- WHY NEEDED:
  Enterprises require user authentication, team workspaces, and API token generation.
- EXECUTION PROCESS:
  1. Add JWT OAuth2 authentication (Admin, Auditor, Viewer roles).
  2. Expose versioned endpoints: `/api/v1/scans`, `/api/v1/sbom/{id}`, `/api/v1/reports/{id}`.
